## Hypothesis

On PR #2014's progressive-3k CaseOps + V21 + #1953 base, reallocating MLP
width from the late layers (6–10) into the looped middle band (3,4,5) — at
roughly fixed total MLP parameters — replicates or exceeds the 040C tie-or-
slight-win seen on the 039-era base. The looped middle is the part doing
repeated refinement; #2014's progressive-context curriculum should reward
extra middle capacity more than the older pre-curriculum stack did.

## Baseline

- PR #2014 head `c9843c9` (simonbissonnette, claimed 3-seed 1.05759, σ 0.00034 vs
  #1953's 1.05855).
- Submission dir:
  `records/track_10min_16mb/2026-04-30_SP8192_CaseOps_Progressive3k_ShortDocTTT/`.
- All settings the author shipped (TRAIN_SEQ_SCHEDULE, EVAL_SEQ_LEN=3072,
  TTT_SHORT_SCORE_FIRST_STEPS, TTT_CHUNK_SIZE=48, etc.) held fixed.
- Uniform width control: `MLP_MULT=4.0` on all 11 physical layers (44.0 width-units total).

## Expected Δ

- 300A on this base, post-EMA pre-quant: **−0.0005 to +0.0010** vs uniform
  baseline. Confidence low — original 040C delta (−0.0002) was within
  single-seed noise on a totally different stack.
- Direction may flip from neutral to positive *if* the progressive-context
  curriculum genuinely loads more work onto the loop band (the case for
  middle-widening); flip to negative if 3072-ctx training already saturates
  loop capacity such that extra width on 3,4,5 mostly steals from late.

## Accept criteria

- 300A wins by ≥ +0.0005 over the same-protocol 4.0 uniform control on the
  pre-quant post-EMA val_bpb at this run length → promote to 8×H100 + 3-seed
  with full quant/TTT pipeline, then write spec 300-followup.
- Within ±0.0005 → tie; do **not** promote. Decision: kill the middle-widen
  hypothesis on this stack.
- 300A loses by > 0.0005 → kill outright.
- All deltas measured at matched train length (same wallclock cap).

## Code changes

Branch `exp/300-040c-on-2014` @ `d174313` adds `MLP_SCHEDULE_ENABLED`,
`MLP_EARLY_MULT`, `MLP_MIDDLE_MULT`, `MLP_LATE_MULT`, `MLP_MIDDLE_LAYERS`
env vars and the helper `_layer_hidden_dims(h)`. Per-layer slicing happens
inside `_bank_weights` (`mlp_up_bank[i, :h]`, `mlp_down_bank[i, :, :h]`).
Banks remain a single tensor sized to `max(layer_hidden_dims)`. Inactive
slices `[i, hidden:, :]` zero-init'd and never read.

## ⚠️ HAZARD — column slice under torch.compile

`mlp_down_bank[i, :, :hidden_dim]` is a non-contiguous column slice. Memory
note `feedback_no_weight_slice_in_compile` says this pattern silently hangs
Triton autotune (GPU pinned at 100%, zero inductor cache files emitted) on
spec 051. **However:** the *exact same* pattern shipped in spec 040 on the
039 base and ran cleanly to step 1300 (logs in
`runs/040-loop-layer-mlp-reallocation-screen-2h/`). The 2014 base is more
compile-aggressive than 039 (full V21 stack + progressive ctx).

**Mitigation:** before launching either arm with the schedule on, run a
60-second compile-only sanity job (4×H100, MAX_WALLCLOCK_SECONDS=120,
PREWARM-style) on `300A` and confirm the loop-active graph compiles without
hanging. If it hangs, escalate to research and refactor `mlp_up_bank` /
`mlp_down_bank` into per-layer `nn.Parameter`s (bigger patch — defer).

If launch succeeds, also compare step-time at step 100 on 300A vs baseline:
the column slice may incur a contiguous-copy on every forward, and a > 5%
step-time gap means the slicing is forcing a data movement that should be
fixed before any 8×H100 promotion.
